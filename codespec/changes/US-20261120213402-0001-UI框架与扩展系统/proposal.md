# obox UI 框架、进程间消息与扩展系统 Proposal

## 背景

obox 现在只是 Python 3.12 的一个空壳：pyproject.toml 只声明了项目名，main.py 打印一行文本，README 为空，既没有 GUI，也没有任何扩展能力。要把它做成「像 VSCode 一样可扩展的桌面程序」，三块地基必须同时到位：声明式界面框架（扩展用 HTML 写法描述组件、用 QSS 定样式、用消息驱动行为）、一条不依赖网络端口的进程间通道（Windows 优先）、一套仿 VSCode 的扩展体系（清单、目录约定、激活/停用生命周期与 context 注入）。缺任何一块，扩展要么画不出界面，要么拿不到界面事件，要么根本没地方被加载。

本次变更首次建立工程基线，一次把三块地基定清，并交付核心组件子集与一份示范扩展，让「扩展激活 → 渲染界面 → 点击按钮 → 扩展收到事件 → 回发状态修改 → 界面更新」这条闭环真实跑通。

## 目标

- 扩展能以 HTML 组件声明 + QSS + 消息的方式构建界面；组件由基于 qfluentwidgets 重写的原生控件组装，全程不引入 Web 引擎。
- obox 与扩展宿主进程之间建立一条无端口的本地通道，同时支持单向通知与请求-应答，请求结果既能阻塞等待，也能通过 Future 或 await 异步获取。
- 扩展按 VSCode 的目录与清单约定开发：extensions/{name}/ 下放 extension.json、assets/ 与 extension.py，入口提供 activate 与 deactivate 并注入 context。
- 交付 12 到 15 个核心组件与一份示范扩展，端到端闭环可演示、可验证。
- obox 自身也走同一套组件与消息通道，保证「obox 命名空间内组件 id 唯一」这条约束有落点。

## 范围

**做：**

- obox/ 主程序包：入口、主窗口装配、HTML 组件 DSL 解析、QSS 主题、消息基类与组件消息封装、命名管道传输、扩展加载与扩展宿主进程。
- obox/api 组件消息封装三件套与返还程标识、关联 id、Future/await 异步框架。
- extensions/ 扩展目录约定，以及一份带 svg 图标、commands 与 views 注册点的示范扩展。
- obox 图标从 tmp/obox.svg 迁入 obox/assets/obox.svg。
- codespec 基线（spec.md、design.md、docs/arch.md、README.md）与本次变更的 delta 文档。

**不做：**

- 扩展市场、在线安装与升级、签名校验、权限沙箱。
- antd 全量组件（只交付核心子集，其余按后续变更迭代）。
- 命令面板、多语言、主题市场等 VSCode 完整外围能力（只保留注册点骨架）。
- 非 Windows 平台的验收（代码保持 Qt 跨平台写法，但只在 Windows 上验证）。
- 扩展热重载（停用后需重启宿主生效）。

## 需求草案

1. 界面框架：解析 HTML 组件文件（PascalCase 组件标签 + 属性），映射到基于 qfluentwidgets 重写的组件并组装成窗体；组件以 id 标识，扩展内唯一、obox 内唯一；QSS 分全局主题与扩展级两层，扩展样式只能命中自己创建的组件。
2. 消息层：基础 Message 携带 src、dst、msg_id，并有返程标识与关联 id；组件消息三件套不可继承、方向固定；dst 为空表示广播且广播无返程；请求方可用 Future、回调或 await 三种方式取结果。
3. 进程通道：obox 侧做服务端、扩展宿主侧做客户端，走 Windows 命名管道，帧格式为 4 字节长度前缀加 UTF-8 JSON，不监听任何 TCP/UDP 端口，断线能重连。
4. 扩展系统：扫描 extensions/ 并校验 extension.json（名称、版本、作者、描述、注册点、svg 图标），在单一扩展宿主进程中激活并注入 context；需要界面时走第 1 条的能力。
5. 单扩展故障不阻断其他扩展激活；宿主进程崩溃后 obox 负责重启并提示。

## 关键取舍

- 渲染栈选 qfluentwidgets 原生控件承载 HTML DSL，否掉 QWebEngineView（安装体积增加 150MB 以上、与桌面外壳割裂、QSS 完全失效）与从零手写 HTML 渲染器（工期与还原度都不可控）。
- 通道选 QLocalServer 与 QLocalSocket 命名管道，否掉 WM_COPYDATA（约 2KB 载荷上限、同步投递会成为高频组件消息的瓶颈）与本地端口（违反「不得使用端口」的硬约束）。
- 进程模型选单一扩展宿主进程，否掉每扩展一进程（组件消息要按扩展路由、进程池与启动开销显著抬高复杂度）。
- 组件消息方向按语义拆分：事件由 obox 发往扩展，状态查询与修改由扩展发往 obox；应答复用原消息类型并加返程标识，否掉「三条消息一律固定 src/dst」（事件方向会变成绕行）与独立应答消息类型（与「复用原有消息」的要求相悖）。
- 异步框架自建 Future（回调 + 阻塞等待 + await 三形态），不引入 qasync，避免把 Qt 主循环与 asyncio 强绑定。

## 与基线的冲突

无。工程此前没有任何 spec 与 design 基线，本次为首次建立；也不存在 docs/adr 决策需要让位。

## 假设

- qfluentwidgets 使用 PySide6-Fluent-Widgets 免费版（GPLv3）；若后续要闭源分发，需要另购商业授权或替换组件库。
- 扩展被视为可信本地代码，v1 不做签名与权限校验。
- v1 的注册点只实现 commands、views、viewsContainers、configuration 四类，其余留扩展位。

## 第二轮追加：可替换 UI 组件库与视觉统一

### 背景

当前 15 个组件、解析器、装配器、注册表与主窗口同处 obox/ui 一个包里，组件直接 import obox.api 的常量；外观沿用 qfluentwidgets 默认值，边框与阴影偏硬、圆角偏小。需求有两条：视觉上更柔和；组件实现独立成可替换的 UI 库，编译为 pyd，obox 运行时从固定目录加载，并可换成另一套（light / dark），运行中也能重载。

### 目标

- 15 个组件从 obox/ui 迁出，分别落在 theme/light 与 theme/dark 两个独立源码包，各自用 Nuitka 编译为 pyd，产物放 .theme/{name}/。
- obox 启动按配置（缺省 light）或命令行参数选定一套 kit，缺 pyd 或缺清单直接报错退出；运行中可请求换另一套，重建视图后生效。
- 视觉统一：圆角取 10px 量级、边框降为 1px 淡色或去掉、阴影改为无或大模糊低透明，外壳与内容区一起变。
- 组件契约不变：标签名、状态名、事件名与现有扩展片段完全兼容，扩展无需改动。

### 范围

**做：**

- theme/light、theme/dark 两个独立包：15 个组件类、组件基类、自带的事件与状态常量、theme.json 清单、主题 QSS（含外壳配色）。
- 构建脚本：一条命令把 theme/{name} 编译为 .theme/{name}/{name}.pyd，构建失败给出明确错误。
- obox 侧：UIProvider 协议、kit 加载器（配置文件、命令行覆盖、重载）、装配器改为从 provider 取组件类、外壳与内容区主题应用。
- 测试改造：绝大多数用例注入假 provider；另加一条加载真实 pyd 的集成测试。
- 文档：README 补构建与切换说明。

**不做：**

- 不换底层：仍是 PySide6 与 qfluentwidgets，不引入 Web 引擎。
- 不做 kit 的签名校验、沙箱与在线分发。
- 不做设置界面里的套件选择（下一轮实现），本轮只做扫描、配置文件与命令行选择。
- 不做换库时的组件状态迁移（视图重建，状态清零）。
- 不改扩展 API、消息协议与 QSS 白名单规则。

### 需求草案

1. kit 清单与发现：每个 .theme/{name}/ 放 theme.json（name、version、mode、entry）与 pyd；obox 按 .obox/config.json 的 theme 字段选择，命令行参数可临时覆盖，缺文件或版本不兼容时报错退出。
2. provider 契约：kit 的入口工厂返回 provider，暴露标签到组件类的映射、kit 元信息（名称、模式、版本）与主题 QSS；组件以类型化方法对外，状态用声明式映射、事件用 on_click 这类具名注册方法，obox 负责消息构造与路由。
3. 组件契约不变：标签名、状态名与事件名沿用现有取值，扩展片段零改动。
4. 视觉统一：两套 kit 各自提供圆角、淡边框、柔阴影的主题常量与 QSS，切换后外壳与内容区同时生效。
5. 运行中切换：收到切换请求后销毁现有视图、按新 kit 重建；新 kit 加载失败时保留原 kit 并报错。
6. 构建与缺失处理：构建脚本产出 pyd 与清单；运行期只认 pyd，缺失即报错退出，不静默回退源码。
7. 测试链路：常规用例用内存假 provider；一条集成用例加载真实 pyd，验证工厂、清单与组件映射。

### 关键取舍

- 打包用 Nuitka --module：产物是独立 pyd，构建慢但贴近发布形态；否掉 Cython 与 pybind11。
- 只打包组件类：解析、装配、注册表仍归 obox，换库只换控件实现；否掉整包进 pyd（会把外壳与总线耦合进去）。
- 只认 pyd、缺了就退出：运行路径唯一、行为可预期；否掉源码回退，代价是开发与测试必须先构建或注入假 provider。
- 主题跟着库走：切 kit 即切整套视觉；否掉主题留 obox（会出现深色组件配浅色外壳）。
- 两套独立组件实现：dark 另写 15 个类，外观自由度最高；否掉共享实现只换主题。
- 重载等于换文件重建：接受 CPython 不能卸载扩展模块、旧模块常驻的事实；否掉子进程隔离（Qt 窗口必须同进程）。

### 与基线的冲突

- 基线 design.md 的 D11（模块布局）写组件在 obox/ui/components；本轮迁到 theme/{light,dark} 并由 pyd 提供，合并阶段要改写 D11。
- 基线 design.md 的 D1（渲染栈）写由 obox/ui/components 承载装配；本轮改为装配器接受 provider 提供的组件类，合并阶段要补一句。
- 基线 spec.md 的「HTML 组件声明与装配」「QSS 样式作用域」行为不变，但实现主体换成 kit；扩展 QSS 白名单仍然只作用于扩展片段。
- 无需求删除或改名；冲突集中在 design 的模块布局与主题归属两处。

### 假设

- 构建机具备 MSVC；缺失时构建脚本给出明确报错而不是半成品。
- 两套 kit 的标签名、状态名与事件名与 obox 契约保持一致，obox 不感知具体实现。
- 重载会重建视图，扩展组件 id 重新注册，界面状态不保留。

## 第三轮追加：全自绘 UI、自绘标题栏与 Flex 布局

### 背景

当前 UI 建立在 qfluentwidgets 上：标题栏来自 FluentWindow，30 个组件是它的子类包装，主窗口、通知与表格都依赖它的绘制。需求有三条：标题栏改为自绘；不再依赖现成组件库，所有控件自己画；新增一个按 flex 规则摆放组件的容器。

### 目标

- 依赖收敛到 PySide6：移除 qfluentwidgets，组件、标题栏、窗口按钮、通知与表格全部用 QWidget 与 QPainter 自绘。
- 无边框窗口加自绘标题栏，拖动、双击最大化、边缘缩放、系统菜单与关闭都由自己实现；Windows 上补 DWM 阴影与圆角。
- 新增 Flex 容器，支持 direction、wrap、justify、align、gap 与 grow，作为放置组件的通用容器。
- 每套主题套件自带默认 QSS；obox 与扩展通过 QSS 调整组件外观，扩展片段与标签契约保持不变。

### 范围

**做：**

- 自绘基础：窗口外壳（无边框、标题栏、四个窗口按钮、边缘缩放）、通知、模态浮层、表格、页签与 15 个组件的绘制。
- Flex 布局引擎：测量与排布，支持主轴对齐、交叉轴对齐、换行、间距与按剩余空间伸缩。
- 主题：每套 kit 提供默认 QSS（背景、边框、圆角、字体与组件基础规则），扩展 QSS 照旧走白名单过滤。
- 图标：侧栏与窗口按钮改用内置 svg 或几何绘制，不再依赖组件库的图标集。
- 两套套件（light 与 dark）同步重写，契约不变。

**不做：**

- 不改扩展 API、消息协议、组件标签与状态名。
- 不做动画系统（悬停过渡、展开收起动画留待后续）。
- 不做跨平台窗口行为，本轮只验收 Windows。
- 不做富文本、虚拟滚动表格这类进阶能力。

### 需求草案

1. 自绘窗口：无边框窗口加自绘标题栏，支持拖动、双击最大化、边缘缩放、最小化、最大化、关闭与系统菜单。
2. 自绘组件：15 个组件不再继承组件库，全部用 QWidget 加 QPainter 绘制前景与状态，背景、边框、圆角由 QSS 提供。
3. 默认样式：每套 kit 附带默认 QSS，覆盖组件与外壳；obox 与扩展可以在其之上覆盖。
4. Flex 容器：新增容器标签，按 direction、wrap、justify、align、gap 与 grow 摆放子组件，尺寸变化时重新排布。
5. 契约不变：标签名、状态名、事件名与扩展片段继续有效，demo 无需改动。
6. 依赖收敛：pyproject 去掉 qfluentwidgets，代码中不再出现它的 import。

### 关键取舍

- 全部自绘而不是保留组件库：外观完全可控，依赖只剩 PySide6，GPLv3 授权问题随之消失；代价是 30 个组件与窗口外壳都要重写。
- QSS 管外观、组件只画前景：QSS 的背景、边框、圆角由 Qt 绘制，组件在 paintEvent 里画内容与悬停/按下/焦点状态；不自研 CSS 引擎，扩展继续写熟悉的 QSS。
- Flex 用自定义布局而不是 QBoxLayout 组合：CSS 的换行与按剩余空间伸缩靠嵌套盒子拼不出来，必须自己测量与排布。
- 无边框窗口加 DWM 阴影：自绘标题栏换来统一外观，用 DWM 保住系统级阴影与圆角，避免窗口看起来像贴在桌面上。
- 新增 Flex 标签而不是给 Div 加属性：Div 继续只做纵向堆叠，两种布局语义不混在一个标签里。

### 与基线的冲突

- 基线 design.md 的 D1（渲染栈）写的是基于 qfluentwidgets 原生控件；本轮改为 QWidget 加 QPainter 自绘，合并时要整段改写。
- 基线 design.md 的 D12（主题套件）写组件实现基于组件库；本轮套件自带默认 QSS，决策要补一句样式来源。
- 基线 spec.md 的「QSS 样式作用域」继续成立，但 QSS 从「可选覆盖」变成「外观的唯一来源」，需求要补默认样式与覆盖顺序。
- 基线 spec.md 的「主界面三段布局」不变，只换标题栏与按钮的实现方式。

### 假设

- Windows DWM 的阴影与圆角接口可用；不可用时退回普通无边框窗口并记录。
- 自绘图标用内置 svg 渲染，不引入图标库。
- Flex 容器首批支持常用子集，超出范围的属性值报错而不是静默忽略。
