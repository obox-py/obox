description: 简化架构与代码的自我拷问——设计期逐个追问流程、类、结构体、函数、字段是否必要、能不能删；实现期新增任何类型与成员前先证明不添加会出问题。只拷问自己，不问用户。
---

目标只有一个：**用最少的构件满足用户要求。** 拷问对象是自己写的设计与代码，不是用户。

判决依据永远是**用户的验收判据**（`spec.md` 的需求与 `proposal.md` 的目标），不是「这样更优雅」。

## 一、设计期（写 `delta-design.md` / `delta-arch.md` 时）

落笔前逐个追问，答不上来就不写：

| 追问 | 判据 |
|---|---|
| 这个流程/步骤能不能不引入 | 不引入，用户的需求还满足吗？满足就删 |
| 这个类或结构体是新概念，还是现有概念的换皮 | 换皮就复用现有的，不新增 |
| 每个字段、参数、方法：谁读它 | 没人读就删 |
| 删掉它，哪条验收判据会失败 | 没有任何一条会失败，就删 |
| 这是为本次需求加的，还是为将来预留的 | 预留的一律不留 |

删除之后必须回头核一遍：**用户要求的东西一样不少。** 删多了和加多了都是错，前者更贵。

## 二、实现期（写代码时）

新增门槛，按顺序过：

1. **默认不新增类、结构体、接口**。要新增，先写一句「现有的哪个类型放不下，为什么」
2. **成员、变量、函数、方法**：先回答「不添加会出什么问题」，说不出问题就不加
3. 这个问题必须在本次的验收判据里；判据里没有，就是投机
4. 同一逻辑复制到第三处才抽函数；只有两处且差异明显就让它重复
5. 不为将来留参数、开关、扩展点；不留「先放着以后可能用」的空实现

## 三、两个模式共用的禁令

- 不写没人读的字段、没人调的私有方法、没人传的参数
- 不重复做上游已经做过的校验；不为一不可能发生的分支写兜底
- 不引入「通用框架」式包装，除非需求里明确要求
- 不因为「更面向对象」「更解耦」就拆类；拆开要能说出具体坏处才拆

## 四、交付时要说清的两件事

- **删了什么**：删掉的构件 + 依据（哪个追问判定的），一条一行
- **加了什么、为什么非加不可**：每个新增类型或成员配一句理由

没有删除也没有新增，就写「无」。

## 五、自检

对每个新构件问：**删掉它，用户的验收会失败吗？** 不会失败就是多余的。
对每个删除问：**留下它，会违反哪条判据？** 违反不了就不该删。

## 边界

- 只拷问自己，不用这套问题去问用户
- 只管简化，不改需求、不改流程、不写产物（产物的表达另见 `df-cheap-talk`）
- 与 `df-tdd` 冲突时：测试需要的 seam 优先，简化不得让测试无法写
- 安全、权限、数据校验不在此列——这些属于「删了会出事」的一类，保留
- **宿主没有 AskUserQuestion 时**：本 skill 只拷问自己、不向用户提问，无回退动作；需要用户裁决时交给调用它的阶段 skill
