---
name: df-task
description: 针对一条 US 变更，读取基线与该变更的 delta 产物，把改动拆成任务并标注每项由主 Agent、subagent 还是后台任务执行，向用户确认拆分方式后创建或更新 task.md。
---

df-task 只做拆分：产出一份 `{df_change_dir}/task.md`。不写实现，不动 spec、design、delta。

## 变量

| 变量 | 用途 | 说明 |
|---|---|---|
| `df_proj_dir` | 工程根 | 重要!!，禁止丢弃 |
| `df_us_id` | 本次变更编号 | 重要!!，禁止丢弃 |
| `df_spec_dir` | `{df_proj_dir}/codespec/specs`，基线所在 | - |
| `df_change_dir` | `{df_proj_dir}/codespec/changes/{df_us_id}`，task.md 落点 | - |

变量缺失时先跑一次 `df-env` 补齐。

## 步骤

### 1. 读输入

按顺序读，缺任何一份都停手并指出缺哪份：

| 文件 | 作用 |
|---|---|
| 基线 spec（`specs/spec.md` 或 `specs/<capability>/spec.md`，可能多份） | 现有能力，判断哪些任务会碰到既有契约 |
| `{df_spec_dir}/design.md` | 现有架构与依赖方向，决定任务边界 |
| `{df_change_dir}/delta-spec.md` | 本次的需求差异，任务要逐条覆盖 |
| `{df_change_dir}/delta-design.md` | 本次的改动落点，任务按它的 `## Changes` 展开 |
| `{df_change_dir}/proposal.md` | 背景与「不做」清单；任务不许越出这个范围 | 可跳过（仅提示） |
| `{df_proj_dir}/docs/arch.md`、`README.md` | 架构现状与对外描述；影响使用方式的改动要单列任务 | 可跳过（仅提示） |
| `{df_change_dir}/delta-arch.md` | 本次增量架构；涉及结构改动时任务要覆盖图里新增/变化的组件 |

再读 `{df_change_dir}/task.md`（若已存在）：本次是**更新**，保住已完成的条目与已有 ID，只增删改需要变的部分。

### 2. 分析并拆分

对着 `delta-design.md` 的 `## Changes` 表格与 `delta-spec.md` 的需求做映射：

- 一条需求可能需要多个任务；一个任务也可能覆盖多条需求，但**每条需求必须至少被一个任务覆盖**
- 任务边界优先落在模块边界上（同一文件尽量不跨任务），否则并行时会互相踩
- **步骤粒度**：一步应当能在几分钟内做完、且能独立验证；把"改 5 个文件"当一个步骤就是切太粗，"加一个 import"就是切太碎
- 每个任务都要能写出**可验证的完成判据**——写不出来说明切得太粗或太虚
- 顺序由依赖决定，无依赖的任务标成可并行

### 3. 标注执行方式

每个任务标一个方式，二选一，判据写死避免随意标：

| 方式 | 什么时候用 |
|---|---|
| `主 Agent` | 单文件或单点小改；需要与用户边做边确认；收尾与整合类任务 |
| `subagent` | 要读大量上下文、跨多文件；与其他任务文件不重叠、可并行；结论比过程重要 |
| `后台` | 长命令、构建、批量生成或重命名；耗时长但不占对话；完成信号可判定（退出码或产物存在） |

拿不准时按`主 Agent`走，别为了并行而并行。

### 4. 向用户确认拆分方式

拆分不是唯一解，把候选方式摆出来让用户选（提问只用 AskUserQuestion，与 `df-grill` 同一形态）：

```js
AskUserQuestion({
  "questions": [
    {
      "header": "拆分方式（也可直接输入你的切法）",
      "question": "这次按哪种方式切任务？我这版是按 <已选方式> 切的，共 <N> 个任务，其中 <M> 个建议派 subagent。",
      "options": [
        {"label": "<推荐方式> (Recommended)", "description": "<为什么适合本次：依赖形态、并行空间、验收粒度>"},
        {"label": "<另一种方式>", "description": "<代价与收益各一句>"}
      ],
      "multiSelect": false
    }
  ]
})
```

三种常见切法：**按需求**（每条 delta-spec 需求一组，验收直观）、**按模块**（每个受影响模块一组，并行度最高）、**按可验证增量**（每个任务自带能跑通的验证点，回滚粒度最细）。推荐哪一种，取决于本次的依赖形态——把理由写进选项描述。

用户改了切法，重排任务再确认一次；确认后才落盘。

### 5. 写或更新 task.md

按 `templates/task.md` 填，落盘到 `{df_change_dir}/task.md`：

- `## 拆分方式`：写最终采用的方式与一句理由
- `## 全局约束`：全流程都要守的约束（不许动的接口、必须保持的兼容性、禁止引入的依赖）；没有就整节删掉
- `## 任务详情`：每个任务一节，含**可独立验证的步骤**、**可复制执行的验收命令**、**自检点**——这是给执行者照做的最小单元，不是给读者看的摘要
- `## 测试策略`：保持"待执行阶段确认"，由执行阶段询问用户后回填；本 skill 不预设 TDD 或常规
- 表格八列齐全，`方式` 只能是 `主 Agent` / `subagent` / `后台`；`状态` 一律初始化为 `待办`
- ID 用 `T1 / T2 ...`；更新已有文件时沿用旧 ID，新增任务接在最大编号之后，不复用已删编号
- `## 覆盖检查` 列出每条需求 → 覆盖它的任务 ID
- `## 执行顺序` 里标出哪些任务可并行
- 模板里的 `<...>` 与 HTML 注释全部替换

### 6. 回读校验

- 每条 `delta-spec.md` 需求都被至少一个任务覆盖；漏一条就补任务
- 每个任务的 `方式`、`涉及文件`、`完成判据`、`状态` 都非空，且 `方式` 在三值之内
- 每个任务在 `## 任务详情` 里都有一节，且 `验收命令` 是可直接复制执行的形态
- `## 测试策略` 保持"待执行阶段确认"，不预设 TDD 或常规
- `## 自检（落盘前）` 的勾选项逐条确认过，不是照抄模板
- 依赖无环：顺着 `依赖` 列走一圈不该回到自己
- 无 `<...>`、`<!-- -->`、`TODO` 残留；frontmatter `status` 改成 `done`

### 7. 简报与确认

收尾前写一段简报（不超过 8 行），直接放进下面提问卡的 `question`，不要另起一段。简报至少包含：

- 落盘路径：`task.md`
- 任务总数；三种方式各几个（主 Agent / subagent / 后台）
- 波次划分与可并行组；覆盖检查是否每条需求都有任务
- 仍然存在的假设（没有就写"无"）

```js
AskUserQuestion({
  "questions": [
    {
      "header": "验收（要改什么就直接输入）",
      "question": "【简报：结论 / 证据 / 风险，不超过 8 行】\n\n符合你的要求吗？不符合就直接输入要改的地方。",
      "options": [
        {"label": "符合", "description": "task.md 定稿"}
      ],
      "multiSelect": false
    }
  ]
})
```

- 只有两类回答：`符合`，或用户直接输入修改意见
- 用户输入 → 按意见改 → 重新出简报 → 再问一次
- **迭代上限 3 轮**；到顶仍未确认，列出未达成项并停手，不再自行修改

## 边界

- **只写一份**：`{df_change_dir}/task.md`。不写 `scope.md`（执行边界是单独一步的产物）、也不写 `spec.md`、`design.md`、`delta-spec.md`、`delta-design.md`、`validation.md`、`arch_*.md`。
- **只拆分不实现**：不写代码、不跑构建、不建分支。
- **不动基线也不动 delta**：它们要改，回到对应的产出步骤，本 skill 不代劳。
- **不改已有的完成状态**：更新时保留已完成任务的标记与 ID。
- **不推进 `df_stage`**。
- **提问只用 AskUserQuestion**。
- **宿主没有 AskUserQuestion 时**：退回编号列表提问，不跳过提问。
