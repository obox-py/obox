TDD 是**红 → 绿循环**：先写一个失败测试，再写刚好能过的实现，重复。这个 skill 只定义怎么让这个循环产出的测试值得留下——它不写文档、不推进任何阶段，规则由调用方执行。

## 循环的四条硬规则

- **先红后绿**：先写失败测试并看到它失败，再写刚好能过的实现。不预写后续测试，不加投机功能
- **一次一个切片**：一个 seam、一个测试、一个最小实现，一循环一轮
- **垂直切片，不许横切**：禁止「先写完所有测试再写实现」——批量写的测试验的是想象出来的行为，等实现真正落地时它们既不够敏感也改不动
- **重构不属于这个循环**：重构归评审阶段，不塞进红绿之间

## 测试只写在约定的 seam

**seam** 是可以从外部观察行为的公共边界——接口，而不是内部结构。测试只落在 seam 上。

写任何测试之前：

1. 列出本次要动的 seam（公共接口 / 命令 / 端点 / 模块导出），一条一行
2. 每条写一句「能抓到什么、抓不到什么」
3. **和用户确认这份清单**；未确认的 seam 不写测试

为什么要先约定：测试不可能覆盖一切，先定 seam 才能把精力压在关键路径和复杂逻辑上，而不是平均撒在每个边界值上。

## 好测试的标准

- **验行为，不验实现**：从公共接口断言。判据是——重构后行为没变，测试不该红
- **期望值必须有独立来源**：已知字面量、手算样例、规格原文。禁止用与被测代码相同的算法算期望值
- **名字读起来像规格**：说明的是「有什么能力」，不是「第几个测试」
- 术语跟项目既有词汇走；本区域有 ADR 的，先读再写

## 三个反模式（出现即返工）

| 反模式 | 识别信号 | 为什么错 |
|---|---|---|
| **实现耦合** | mock 内部协作者、测私有方法、绕过接口去查库 | 重构就红，而行为根本没变 |
| **自证式** | 断言按被测代码的算法重算期望值 | 构造上不可能失败，等于没测 |
| **横切** | 先写一整批测试再写实现 | 验的是想象中的形状，锁定的是实现前的猜测 |

## 什么时候不适合 TDD

不是所有改动都值得走红绿循环。以下情况先与调用方确认，别硬套：

- 纯配置、纯文案、纯格式调整
- 探索性原型：接口还没定型，先探路再补测试
- 一次性脚本或迁移工具，跑完即弃

除此之外，行为改动一律走循环。

## 与验收命令的关系

TDD 模式下，任务的**验收命令必须包含测试命令**——否则「测试通过」只是口头结论，回归记录里也拿不出证据。

## 边界

- **不写任何文档**：不产出 spec/design/delta/task/validation/review，也不回填 `## 测试策略`（那一行由调用方写）。
- **不改代码**：规则由调用方执行，本 skill 不代替它动手。
- **不推进 `df_stage`**。
- **不在未确认的 seam 上写测试**。
- **宿主没有 AskUserQuestion 时**：退回编号列表提问，不跳过提问。
