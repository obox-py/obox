name: df-review
description: 对本次变更发起并接收一次代码评审——组评审包、按规格与规范两轴找问题、逐条先验证再定接受或反驳，把意见、修复与回归证据写进 review.md。
---

df-review 做两件事：**发起一次有据可查的评审**，以及**接收意见时先验证再表态**。它不改需求、不改 delta、不重构；代码改动只在评审项范围内。

## 变量

| 变量 | 用途 | 说明 |
|---|---|---|
| `df_proj_dir` | 工程根 | 重要!!，禁止丢弃 |
| `df_us_id` | 本次变更编号 | 重要!!，禁止丢弃 |
| `df_change_dir` | `{df_proj_dir}/codespec/changes/{df_us_id}`，review.md 落点 | - |
| `df_spec_dir` | `{df_proj_dir}/codespec/specs` | - |

变量缺失时先跑一次 `df-env` 补齐。

## 步骤

### 1. 守门

| 条件 | 不满足时 |
|---|---|
| `task.md` 里所有任务都是 `完成` 或已记 `阻塞` | **停手**，回 `df-solver` |
| `validation.md` 没有"待用户决策"的严重项 | **停手**，先把问题定下来 |
| 每个 `完成` 任务都留着验收命令与输出 | **停手**：没有证据的完成不算完成 |
| `scope.md` 存在且白名单非空 | **停手**，回 `df-task`：没有边界就无法判断有没有越界 |

### 2. 组评审包

评审不能凭印象，先把上下文摊开（写进 `review.md` 的 `## 评审包`）：

- **变更范围**：改了哪些文件、增删多少行（`git diff --stat` 或等价手段）
- **对应需求**：本次触及的 delta-spec 需求名，逐条列出
- **验证证据**：每个任务的验收命令与结果
- **长度登记核对**：`## 长度超阈值` 里的每一行，都要能对上真实代码位置与行数；编不出来的理由按缺失处理
- **架构一致性**：本次实现是否与 `{df_change_dir}/delta-arch.md` 里的待改模块、依赖方向一致；超出增量架构范围的改动要单列
- **边界比对**：`git diff --name-only`（或等价手段）列出的每个文件，逐个对 `scope.md` 的白名单；白名单外的文件单独列出，**每一条都是严重项**

然后逐条走一遍作者自查。**自查不过就不许进评审**——把问题交给评审者，等于让人替你收拾。

### 3. 评审（两轴）

| 轴 | 查什么 | 依据 |
|---|---|---|
| 规格轴 | 每条 delta-spec 需求是否真的实现；每个 Scenario 能否复现；实现是否还在 proposal 的目标与「不做」范围内；**改动是否都在 `scope.md` 白名单内** | `proposal.md`、`delta-spec.md`、`delta-design.md`、`scope.md` |
| 标准轴 | 代码规范与坏味道；**必要性**（判据见 `df-simple`）：未使用符号、过度抽象、单调用却独立成函数、不可能发生的防御分支、为将来预留的参数、新增类型缺少「不加会坏什么」的理由；**长度**：函数 > 40 行或文件 > 400 行的，是否在 `## 长度超阈值` 里有站得住的原因 | `../df-solver/references/<语言>.md`、`scope.md` |
| 测试轴 | `task.md` 的 `## 测试策略` 写了 TDD 时：按 `df-tdd` 的标准核对"先红后绿"证据、测试是否落在约定的 seam、期望值是否自证 | `task.md`、`## 回归` |

- **评审者与作者尽量分离**：把评审包交给一个 subagent 做独立评审，比自评有效；不给它本次改动的实现思路，只给评审包与规范文档路径，避免它顺着你的说法找证据
- 每条意见都要带**档位 / 位置 `文件:行` / 证据**（命令输出或代码引用），没有证据的判断不许进清单
- 分档：**严重** = 行为错误、安全问题、数据损坏、需求未满足；**一般** = 缺错误处理、边界不清、可维护性差；**建议** = 风格与优化

### 4. 接收（先验证再表态）

对每条意见，**先自己复核再决定**，三种结论：

- `接受`：确认成立，按意见改
- `部分接受`：写清哪部分成立、哪部分不成立及理由
- `反驳`：给出证据（代码位置、命令输出、需求原文）

禁止"好建议，照做"式的全盘接受，也禁止因为"是评审者说的"就放弃验证。评审意见是证据，不是命令。

### 5. 修复与回归

- 只改评审项涉及的代码，不顺手重构、不扩范围
- 每改一条，重跑受影响的验收命令与 `check.py`，把命令与结果记进 `## 回归`
- 若改动触及 delta-spec 的需求或 delta-design 的结构：先让上游更新 delta，再让 `df-solver` 重跑基线合并——**基线必须与最终代码一致**

### 6. 写 review.md

按模板填，落盘到 `{df_change_dir}/review.md`：

- `## 意见清单` 每行一条，`档位` 只取 `严重` / `一般` / `建议`，`结论` 只取 `接受` / `部分接受` / `反驳`
- `## 回归` 一条修复一行，写清命令与结果
- `## 结论` 里**严重剩余必须为 0**；还有严重项就不许把 `status` 改成 `done`
- 一般与建议项转入 `validation.md` 的遗留或新任务，不要留在 review.md 里自然消失
- 模板里的 `<...>` 与注释全部替换

### 7. 简报与确认

简报（不超过 8 行）写进下面提问卡的 `question`：评审包摘要（几个文件、几条需求）、意见分档与结论分布、修复了哪些、回归结果、剩余项去向。然后提一题：

```js
AskUserQuestion({
  "questions": [
    {
      "header": "验收（要改什么就直接输入）",
      "question": "【简报：结论 / 证据 / 风险，不超过 8 行】\n\n评审结论符合你的要求吗？不符合就直接输入要改的地方。",
      "options": [
        {"label": "符合", "description": "review.md 定稿，可以进入收尾"}
      ],
      "multiSelect": false
    }
  ]
})
```

- 只有两类回答：`符合`，或用户直接输入修改意见
- 用户输入 → 按意见改 → 重新出简报 → 再问一次
- **迭代上限 3 轮**；到顶列出未达成项并停手

## 边界

- **只写 `{df_change_dir}/review.md`**：不改 `spec.md`、`design.md`、`delta-*`、`task.md`、`validation.md` 正文，也不写 `README.md`。
- **代码改动仅限评审项**：不顺手重构、不扩范围、不改需求。
- **不做合并**：基线合并归 `df-solver`，架构合并归 `df-init`。
- **不推进 `df_stage`**。
- **评审意见不等于命令**：每条都要先验证再表态。
- **提问只用 AskUserQuestion**。
- **宿主没有 AskUserQuestion 时**：退回编号列表提问，不跳过提问。
